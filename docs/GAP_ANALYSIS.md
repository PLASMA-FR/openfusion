# OpenFusion Gap Analysis

**Baseline under evaluation:** FreeCAD 1.1.3, commit `145529fe741292ff0b3977a01195bf0247425794`

**Assessment date:** 2026-08-29

**Production-ready:** No

This document separates inherited FreeCAD capability from verified OpenFusion product work. “Inherited” does not mean accepted, integrated, regression-tested, or supported by an OpenFusion release. No area may move to “Gate passed” without committed test and acceptance evidence.

## Highest-priority gaps

1. Record a reproducible untouched build, tests, launch, save/reopen smoke test, and performance baseline.
2. Implement and test the M1 Design workspace spine without changing document serialization or modeling commands.
3. Establish the core acceptance model and undo/save/reopen regression harness.
4. Build the functional Part Design timeline only after the shared selection and workspace context are stable.
5. Verify import/export and data-safety behavior before major visual refactoring.
6. Establish cross-platform CI and packaging smoke tests before making platform-support claims.

## M1 vertical-slice evidence required

The gap for the first slice closes only when all of the following are recorded:

- Design selection activates the actual `PartDesignWorkbench`.
- Legacy or Python workbench activation updates the workspace selector without a loop.
- Face, edge, sketch, body, and empty selections expose the intended registered commands.
- Context-strip and palette commands use normal FreeCAD command, task, undo, and macro behavior.
- Lazy module command registration refreshes search results.
- Tree and viewport selection produce identical context state.
- Command palette keyboard, focus, disabled-state, fuzzy-ranking, and cancellation tests pass.
- Body → sketch → pad → fillet → save → close → reopen → edit → undo/redo passes.
- Closing a document or deleting a selected object during a queued context refresh does not crash.
- No OpenFusion-specific property is written to an FCStd document by the shell.

## Update rule

Update this table after every substantial milestone. Each status change must point to code, test output, a recorded manual acceptance result, benchmark data, or a package-install report. Screenshots alone do not close a functional gap.
